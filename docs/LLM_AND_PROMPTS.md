# LLM / VLM: подключение, применение и промпты

Языковые и мультимодальные модели — **опциональные** тяжеловесные экстракторы (ТЗ, табл. 5–6).
Пайплайн полностью работает без них (`LLM_MODE=off`): вердикт, коды причин и правила формируются
детерминированными экстракторами. LLM дополняют анализ и никогда в одиночку не выносят вердикт «фишинг».

## Подключение

Поддерживается любой сервер с OpenAI-совместимым методом `chat/completions`.

| Режим | Переменные | Примеры |
|---|---|---|
| `LLM_MODE=local` | `LLM_LOCAL_BASE_URL`, (опц.) `LLM_LOCAL_API_KEY`, `LLM_LOCAL_TEXT_MODEL`, `LLM_LOCAL_VISION_MODEL` | в Docker — контейнер `llm` (Ollama, `http://llm:11434/v1`); вне Docker — Ollama `http://localhost:11434/v1`, LM Studio `http://localhost:1234/v1`, vLLM |
| `LLM_MODE=cloud` | `LLM_CLOUD_BASE_URL`, `LLM_CLOUD_API_KEY`, `LLM_CLOUD_TEXT_MODEL`, `LLM_CLOUD_VISION_MODEL` | удалённый сервер с доступом по API-ключу; только открытые и собственные данные |
| `LLM_MODE=off` | — | только детерминированные экстракторы |

У каждого режима свои модели. Если модель для изображений не задана, используется текстовая (она должна
быть мультимодальной). Ключ хранится только в `.env` (не в репозитории).

**Локальный контур в Docker.** Контейнер `llm` (Ollama) подключён только к внутренней сети `llm_net`
без выхода в интернет: данные не покидают контур (ТЗ 4.4.2). Модели один раз скачивает `llm-init` в том
`llm_models`; если они уже там, интернет не нужен. По умолчанию — `qwen3-vl:2b-instruct`: одна мультимодальная
модель для текста и изображений. Используются варианты `-instruct`: «рассуждающие» варианты на CPU тратят
на скрытые рассуждения больше минуты на вызов.

Замер на ноутбуке (Intel Core Ultra 9 285H, CPU, 15.10.2026):

| Модель | Текст письма | Изображение |
|---|---|---|
| `qwen3-vl:2b-instruct` | 4–7 с | ~35 с |
| `qwen3-vl:4b-instruct` | ~16 с | ~57 с |
| облачная `Qwen3.8-27B` (с рассуждениями) | 3–7 с | < 1 с |

Облачной модели рассуждения нужны: без них (`LLM_REASONING_EFFORT=none`) она ошибается на приманках без
явного запроса данных. Рассуждения расходуют бюджет `LLM_MAX_TOKENS` (по умолчанию 4000), поэтому он больше,
чем длина ответа.

Поведение клиента (`services/worker/src/llm/client.py`):
- повтор запроса только при 429/5xx; ошибки 4xx (неверная модель, ключ) не повторяются;
- если локальный сервер не запущен — клиент перестаёт к нему обращаться на 60 с (пакетная обработка не замедляется);
- «рассуждения» модели (`reasoning_content`) никогда не используются как ответ;
- каждый вызов журналируется в `logs/llm_audit.log` (модель, промпт, ответ, время) и в трассировке агента.

## Где применяются модели

| Агент | Модель | Задача | Как используется результат |
|---|---|---|---|
| Vision Agent | VLM | бренд и тип приманки по снимку страницы/вложения, если бренд не найден в заголовке и отправителе | бренд сверяется с реестром и allowlist; `BRAND_IMPERSONATION_CONFIRMED` только при уверенности ≥ 0.5 и бренде из реестра |
| Content Agent | LLM | классификация текста письма/страницы как социально-инженерной приманки (в т.ч. письма без ссылок «ответьте на письмо») | код `CONTENT_LLM_LURE` (вес 0.45) только при уверенности ≥ 0.75 — сам по себе даёт максимум «подозрительно» |
| Synthesizer | LLM | текстовое заключение для аналитика на русском | добавляется к детерминированному обоснованию по кодам причин, на вердикт не влияет |

Ответы VLM и Content Agent кэшируются (по хешу изображения / текста) — одинаковые kit'ы не анализируются повторно.

## Промпты

Хранятся в репозитории: `services/worker/src/prompts/*.txt` (шаблоны `string.Template`, подстановки `$name`).

| Файл | Назначение | Формат ответа |
|---|---|---|
| `vision_brand.txt` | какой бренд страница/изображение **выдаёт за себя** (не платёжные логотипы и партнёры), прочие видимые бренды, какого действия требует изображение, тип приманки. Бренд от VLM подтверждает имитацию только при запросе данных (формы или `asks_user_action` = ввод учётных данных / карты); «тип документа» — улика только при требовании действия | JSON `{"impersonated_brand", "other_brands", "asks_user_action", "lure", "login_form_visible", "logo_box", "confidence", "reason"}` |
| `lure_classifier.txt` | классификация текста приманки; на входе тема, отправитель, домены ссылок письма (без путей и параметров), текст письма, текст страницы, текст вложений и OCR картинок (до 3 вложений) | JSON `{"is_phishing_lure", "lure_type", "confidence", "indicators"}` |
| `analyst_summary.txt`, `analyst_summary_system.txt` | заключение SOC-аналитика строго по переданным фактам | свободный текст (2–3 предложения) |

Дообучение (в т.ч. LoRA) не выполняется.

## Журналы для разбора прогонов

- `logs/llm_audit.log` — короткая человекочитаемая запись каждого вызова (как раньше).
- `logs/llm_audit.jsonl` — одна строка JSON на вызов: объект (`object` = `incident_id`), промпт (`prompt_name`,
  `prompt_version` — первые 8 символов SHA-256 файла промпта), полный текст промпта и ответа (до 20 000 символов, без
  байтов изображения; для VLM — `image_sha1`), число попыток и ошибки повторов (`attempts`, `retried_errors`),
  `finish_reason`, `usage`, итоговая ошибка.
- В отчёте метрик у каждого объекта — `incident_id`, `llm_degraded` и `diag`: признаки с весами и деталями, бренд и его
  источник, полный разобранный ответ VLM и LLM, наличие скриншота, вызовы модели с версиями промптов, время агентов.
- Раздел `diagnostics` отчёта (и `summary.json` размеченного набора): пропуски по причинам (нет признаков / ниже порога),
  объекты у порогов, флаги на легитимных с ответами модели, обнаружения на одном признаке, покрытие скриншотами,
  статистика модели (сбои, задержки, версии промптов, ответы VLM, «модель сказала приманка — вердикт чисто» и наоборот).
- `phishctl.py diff-runs A B` — сравнение двух прогонов по объектам: переходы вердиктов по категориям и признаки,
  которые появились / исчезли у каждого изменившегося объекта.
