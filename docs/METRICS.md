# Методика расчёта метрик и отчёт о метриках

Все метрики рассчитываются одной командой и сохраняются в JSON (ТЗ п. 4.1.11, принцип «проверяемость»):

```bash
python phishctl.py split --seen-from reports/seen_objects.txt          # разбиение корпуса (один раз)
python phishctl.py metrics --part dev --limit 300 --workers 3 --out reports/dev.json
python phishctl.py metrics --part test --workers 3 --out reports/test.json   # итоговая оценка
python phishctl.py robustness --limit 40 --out reports/robustness.json        # на отложенной части
python phishctl.py eval-labeled file_for_case/antiphishing_eml_540_combined --out reports/labeled_eval
python phishctl.py diff-runs reports/test_prev.json reports/test.json         # что изменилось и почему
```

> **Статус 17.10.2026.** Система переведена на обязательную модель (LLM/VLM), словари и режим без модели
> удалены. Все результаты ниже получены прежними версиями (в основном без модели) и будут заменены прогонами
> текущей версии. Объекты, на которых модель не ответила после всех попыток, получают статус `skipped_llm`:
> они снижают полноту обработки, а `recall_counting_skipped_as_missed` считает их промахами.

> **Статус 27.10.2026 (изменения после 17.10).**
> - Вердикт «фишинг» требует признаков минимум из двух независимых групп (ТЗ 4.1.4.6, `rules/reason_codes.py::INDEPENDENCE_GROUPS`);
>   одиночные критичные коды (ScreenConnect, Telegram/Discord-эксфильтрация) дают «подозрительно». Recall «фишинг + подозрительно»
>   это не меняет, меняется доля «фишинг».
> - Страницы HTML исполняют сценарии в закрытом браузере песочницы (сеть заблокирована): итоговый DOM, отложенная загрузка,
>   адреса, куда сценарий пытается перейти (ПМИ А-5, ТЗ 4.1.4.2). Прежние цифры по HTML получены без этого.
> - Добавлены baseline-классификатор (`phishctl.py baseline`) и метрика полноты извлечения (`phishctl.py extraction-eval`), см. ниже.
> - Локальный режим (Ollama, `qwen3-vl:2b-instruct`, CPU, изолированная сеть) подтверждён на объекте; замер на выборке отложенной
>   части — раздел «Локальная модель».
> - Все цифры разделов выше посчитаны версиями до этих изменений; прогон с моделью на отложенной части текущей версией — только локальный
>   (выборка), облако для данных Заказчика не использовалось.

## Baseline-классификатор HTML (ТЗ 4.1.3.2–4.1.3.4, 4.1.11)

Интерпретируемое дерево решений (CART, глубина ≤ 4) на сырых признаках страницы (число форм, внешних скриптов, фреймов, маркеров
обфускации и т. п.; `services/worker/src/baseline.py`), модель `models/baseline_v1.json` (версия — хеш содержимого, значимость
признаков и путь решения в файле). Обучение — на HTML-вложениях части настройки (не более 8 страниц на DOM-шаблон) против
легитимного HTML (страницы набора Разработчика и HTML-тела легитимных писем, 70 % по хешу id). Оценка — на отложенной части.

| Метрика (отложенная часть, HTML-вложения, 1 438 объектов) | Baseline | Конвейер без LLM (`test_v3`) |
|---|---|---|
| Recall (baseline — «фишинг»; конвейер — «фишинг + подозрительно») | **0.819** | 0.715 |
| Recall по DOM-шаблонам (675 шаблонов) | 0.914 | — |
| Ложные срабатывания на легитимном HTML отложенной части | **2 из 10** | 0 из 34 (набор конвейера) |
| Объяснимость | путь по дереву | коды причин с уликами |

**Как читать.** Baseline находит больше фишинговых HTML (226 объектов, пропущенных конвейером, 77 — наоборот), но ценой ложных
срабатываний: 2 из 10 легитимных объектов (требование ТЗ — 0). Оценка ложных срабатываний baseline — грубая: легитимного HTML мало
(≈ 70 объектов, в основном тела писем и синтетические страницы), главный признак модели — число внешних скриптов, то есть он
частично отличает «вложение письма» от «обычной страницы». Поэтому baseline подтверждает, что у корпуса есть отличимые структурные
признаки, но не заменяет конвейер, который держит 0 ложных; его цифры — точка сравнения по п. 4.1.11, а не рабочий результат.
Отчёт: `reports/baseline_eval.json`.

## Данные

| Набор | Состав | Метка |
|---|---|---|
| `keis2_email` | письма целевых брендов (EML + собранные ссылки `Link_N`) | фишинг |
| `html_attachment` | HTML-вложения (`html_phishing2026`) | фишинг |
| `image_lure` | изображения-приманки (`grouped_png_phishing2026`) | фишинг |
| `benign_page`, `benign_email` | заведомо легитимные объекты, собранные Разработчиком (`tests/fixtures/benign_samples.py`): страницы входа брендов на официальных доменах, агрегатор банков с формой входа, чекаут магазина с логотипами платёжных систем, корпоративный SSO, дочерние компании брендов, рассылки брендов, счёт с PDF, личная переписка | легитимный |

`--limit N` ограничивает число объектов на источник. С `--part` выборка детерминированно «перемешана»
(порядок по sha256 имени файла), поэтому охватывает разные шаблоны и кластеры, а не первые папки.

### Разбиение корпуса без утечек (ТЗ п. 4.1.3.3, 7.3)

`phishctl.py split` делит корпус Заказчика на часть **настройки** (dev, ≈30 % групп) и **отложенную часть**
(test). Делятся группы, а не объекты, чтобы одна кампания / один шаблон не оказались по обе стороны:

| Источник | Группа | dev: объектов / групп | test: объектов / групп |
|---|---|---|---|
| `keis2` | папка бренда | 331 / 146 | 40 / 26 |
| `html_phishing2026` | хеш остова DOM (последовательность тегов) | 6204 / 378 | 1438 / 675 |
| `grouped_png_phishing2026` | кластер Заказчика (`noise` — каждый файл отдельно) | 1276 / 231 | 1578 / 519 |

Все объекты, которые просматривались при разработке (`reports/seen_objects.txt`), принудительно отнесены к dev
вместе со своими группами. Манифест `reports/split.json` фиксирует назначение каждого объекта (воспроизводимость).
Признаки и веса настраиваются только по dev; отложенная часть используется только для итоговых цифр.

## Метрики

| Метрика | Определение | Цель (ТЗ, табл. 3) |
|---|---|---|
| `processing_completeness` | доля объектов корпуса, обработанных без ошибки | ≥ 0.85 |
| `recall_phishing_plus_suspicious` | доля фишинговых объектов с вердиктом «фишинг» или «подозрительно» | — |
| `recall_template_split` | то же, по одному представителю на каждый DOM-шаблон (остов DOM); исключает завышение за счёт преобладающих kit'ов | ≥ 0.90 |
| `benign_false_phishing` | число вердиктов «фишинг» на легитимных объектах | 0 |
| `benign_suspicious_share` | доля «подозрительно» на легитимных объектах | ≤ 0.10 |
| `reason_code_coverage` | доля вердиктов с кодами причин | 1.0 |
| `light_engine_recall` | доля фишинговых объектов, обнаруживаемых **только** пакетом правил лёгкого модуля (без тяжёлых экстракторов) | — |
| `light_engine_agreement_with_heavy` | доля срабатываний лёгкого модуля, совпадающих с вердиктом пайплайна | — |
| `light_engine_benign_hits` | срабатывания правил пакета на легитимных объектах | 0 |
| `mean_seconds_per_object` | среднее время анализа объекта | ≤ 10 с без LLM |
| `robustness.<сценарий>.recall_drop` | падение recall после замены домена/URL, изменения оформления, отложенной загрузки (на объектах, обнаруженных до изменения) | — |

Отчёт также содержит разрез по источникам, частоту техник (глобальная интерпретация, п. 4.1.5.2),
список пропусков и ложных срабатываний для разбора ошибок.

Какие сохранённые отчёты показывает страница «Метрики» интерфейса, задаёт файл `reports/index.json`:
разделы `corpus`, `labeled`, `robustness`, в каждом список `{"path", "label", "note"}`, где `path` — путь
относительно `reports/`, а в `note` указываются модель и версия кода. Без этого файла используются имена
по умолчанию (`metrics.json`, `labeled_eval_off/`, `labeled_eval_llm/`, `robustness.json`).

примере. Поскольку исправление сделано после просмотра ошибок теста, столбец «после исправления» не является
независимой оценкой — оба значения приведены.

**Вклад LLM.** Агент анализа текста приманки сработал на 33 из 40 фишинговых писем и ни на одном из 500
легитимных. Модель подключалась в облачном режиме с согласия владельца данных; в эксплуатации по ТЗ
(п. 4.5.2.2) используется локальная модель (`LLM_MODE=local`).

**Разбор ошибок (с LLM):**
- пропущено 3 письма: 2 англоязычных текстовых письма без ссылок (модель не дала уверенность ≥ 0.75)
  и письмо «Wildberries», все ссылки которого недоступны (нет страниц для анализа);
- «подозрительно» на легитимных (4): рассылки со ссылками на загрузку `.exe`, ссылкой на IP-адрес и
  несовпадением текста ссылки с адресом — допустимая по ТЗ пограничная зона;
- 8 фишинговых писем получили «подозрительно», а не «фишинг»: подмена отображаемого имени отправителя
  при недоступных ссылках — одиночная улика по политике вердиктов (п. 4.1.4.6) не даёт «фишинг».

из 1 438; письма `keis2` 37 / 37 из 40.

«Подозрительно» на легитимных — два объекта: корпоративный SSO, отправляющий пароль на домен IdP, и изображение-
инструкция «введите логин и пароль» (запрос пароля на изображении) — пограничная зона, допустимая по ТЗ.

На части настройки (900 объектов, «перемешанная» выборка) те же изменения дали 0.672 → 0.864 (по шаблонам
0.561 → 0.822). Расхождение с отложенной частью объясняется составом: в dev попал крупнейший шаблон HTML-вложений
(2 267 копий одного kit'а), который распознаётся хорошо; отложенная часть разнообразнее. Поэтому в отчёт идут
цифры отложенной части.

### Что изменено по результатам разбора ошибок на части настройки

| Причина пропусков | Решение | Коды причин |
|---|---|---|
| Изображения-приманки «защищённый документ, введите пароль» без ссылок и разметки | OCR (Tesseract, локально в песочнице; латиница/кириллица и китайский — отдельными проходами), признаки на тексте изображения; поле `login_form_visible` ответа VLM | `IMAGE_CREDENTIAL_PROMPT`, `IMAGE_FAKE_DOCUMENT_VIEWER`, бренд из текста изображения → `BRAND_IMPERSONATION_CONFIRMED` |
| HTML-письма вебмейл-kit'ов («пароль истекает», «письма задержаны») | детерминированные шаблоны фраз (en/ru/ja/de/cs), обращение по адресу ящика, CAPTCHA внутри вложения | `CONTENT_ACCOUNT_THREAT`, `CONTENT_VICTIM_ADDRESSED`, `ATTACH_FAKE_HUMAN_CHECK` |
| Ссылки внутри HTML-вложений не проверялись | IPFS-шлюзы, бесплатный хостинг ссылки вложения, рекламные open redirect | `URL_IPFS_LINK`, `URL_FREE_HOSTING`, `RC_REDIRECT_ABUSE_TRUSTED` |
| Имя отправителя с подменой букв («МONEX», «MOＮEX») | нормализация полноширинных и кириллических/греческих букв внутри латинских слов; японские названия брендов в базе | `EMAIL_DISPLAYNAME_OBFUSCATED`, `RC_BRAND_SPOOF_DISPLAYNAME` |

Все новые признаки — одиночные улики средней силы: каждый сам по себе даёт не более «подозрительно»
(п. 4.1.4.6), каждый сопровождается подтверждающим фрагментом (п. 4.1.5.1).

Независимая проверка на размеченном наборе из 540 писем (не использовался при настройке): recall без LLM
0.825 → **0.875**, ложных «фишинг» 0, «подозрительно» на легитимных без изменений (4 из 500).

### Анализ недостижения recall ≥ 0.90 (п. 8.4)

- **страницы-загрузчики** (заглушка «Please wait…», содержимое подгружается сценарием с сервера): в сохранённом HTML
  нет формы и текста приманки, без сети и без анализа смысла страницы признаков нет;
- **мошеннические сайты без форм** (фейковые банки, ставки, казино, магазины): не содержат технических признаков
  перехвата данных; по определению ТЗ это мошенничество, а не сбор учётных данных, — распознаются только по смыслу (LLM);
- **изображения с мелким бледным текстом** (подписи полей ввода): OCR не читает, распознаётся только VLM;
- **недоступные ссылки** в письмах: страниц для анализа нет, остаются признаки письма.

План: локальная LLM/VLM (Ollama, Qwen) на отложенной части — анализ смысла страницы и изображения; агент-
обобщатель, переносящий найденные моделью техники в правила лёгкого модуля; активное раскрытие ссылок
(`live-fetch`) для загрузчиков.

### Исторические замеры (до разбиения корпуса)

Первые 300 объектов каждого источника, без LLM: recall 0.747, по шаблонам 0.702; с облачной LLM на 90 объектах —
0.833 / 0.811. Эти цифры получены на выборке, по которой велась разработка, и не являются независимой оценкой.

## Устойчивость к обходу

`phishctl.py robustness --limit 40`: объекты, обнаруженные до изменения, анализируются повторно после изменения.

| Сценарий | Объектов | Recall | Падение recall |
|---|---|---|---|
| Замена домена и URL | 24 | 1.00 | 0.00 |
| Изменение оформления (стили, классы, текстовая «набивка») | 59 | 1.00 | 0.00 |

Сценарий «замена домена» выявил ошибку выбора основной страницы среди нескольких ссылок письма (исправлено до
итогового прогона).
